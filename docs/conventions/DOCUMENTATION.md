# DOCUMENTATION.md — 文档规范

## 1. 核心原则

1. **代码是事实，文档是承诺。** 两者冲突时，要么改代码，要么改文档；不允许“先这样放着”。
2. **一个主题只有一个主档。** 其他位置只能链接过去，不复制表格与数字。
3. **文档有保质期。** 历史材料必须显式标注“仅供追溯”，不能与现行说明混放。
4. **过期即缺陷。** 文档与实现不一致，与代码 bug 同级处理，必须修复或登记到
   [BACKLOG](../plan/BACKLOG.md)。
5. **可验证。** 每条命令、路径、默认值都应能在仓库里找到对应实现。

## 2. 文档分类与存放位置

| 类型 | 目录 | 回答的问题 | 是否现行 |
|------|------|-----------|---------|
| 入口 | `README.md`、`AGENTS.md` | 这是什么、怎么跑、从哪读起 | ✅ 现行 |
| 规范 | `docs/conventions/` | 必须遵守什么 | ✅ 现行 |
| 系统事实 | `docs/architecture/` | 现在如何工作、配置有哪些、接口是什么 | ✅ 现行 |
| 决策 | `docs/decisions/` | 为什么这样选，替代方案与复审条件 | ✅ 决策仍有效 |
| 计划/待办 | `docs/plan/` | 接下来做什么、已知问题 | ⏳ 有保质期 |
| 变更记录 | `docs/changes/` | 某次非平凡改动做了什么、如何验证 | 📌 一次性 |
| 审查/审计 | `docs/reviews/` | 某时点的审计、验收证据 | 📌 一次性 |
| 迭代历史 | `docs/history/iterations/` | 每次迭代当时怎么做 | ❌ 仅供追溯 |
| 原始日志 | `docs/history/` | 旧版本流水记录 | ❌ 仅供追溯 |

历史材料开头必须有“**历史材料，不代表当前实现**”的提示；现行文档不得引用历史文档作为操作依据。

## 3. 命名

- 目录与文件名使用英文大写短横线：`ARCHITECTURE.md`、`HTTP-API.md`、`0001-reactor.md`。
- 决策使用四位序号：`docs/decisions/0001-*.md`，一经接受不再改号。
- 变更记录：`docs/changes/YYYY-MM-DD-<slug>.md`。
- 审查记录：`docs/reviews/YYYY-MM-DD-<TOPIC>.md`。
- 不再使用 `项目日志.md` 这类散落在根目录的中文文件名；根目录只放入口文件。

## 4. 链接规则

- 只使用**仓库内相对链接**：`./docs/...`、`../architecture/...`。
- 禁止：`file:///...`、`/project/CPPReactor/...`、`C:\...`、指向仓库外本机路径的链接。
- 代码位置引用使用 `路径:行号` 文本（如 `src/app/main.cpp:73`），不保证行号永久有效；
  行号失效时以路径和函数名为准。
- 锚点链接必须与标题实际 slug 一致。
- 提交前运行：`python3 scripts/check_docs.py`（检查断链与禁止的绝对路径）。

## 5. 新鲜度：改代码时必须同步什么

| 改动区域 | 必须检查/更新 |
|----------|--------------|
| 启动参数、默认值、路径语义 | `docs/architecture/CONFIGURATION.md`、README「配置」 |
| `SQLConfig` 字段的读取/生效行为 | `CONFIGURATION.md` 的字段表（尤其“是否生效”） |
| 路由、状态码、请求/响应格式 | `docs/architecture/HTTP-API.md` |
| 模块职责、线程模型、扩展点 | `docs/architecture/ARCHITECTURE.md` |
| 构建方式、依赖、镜像 | README「环境要求/快速开始/Docker」、`tests/README.md`（若涉及测试） |
| 测试命令或档位 | `tests/README.md`、README「测试与压测」 |
| 版本号或发布 | `CHANGELOG.md`、`docs/conventions/VERSIONING.md` 的流程 |
| 架构选型改变 | 新增 `docs/decisions/` 记录，并更新 `docs/decisions/README.md` |

无法在同一提交内完成同步时，必须在 [BACKLOG](../plan/BACKLOG.md) 登记，并写明“哪个文档、哪段、
为什么暂缓”。

## 6. 写作要求

- 先给结论/表格，再给解释；命令必须可直接复制执行。
- 默认值、上限、超时等数字必须来自代码或配置，不凭记忆。
- 区分“事实”与“建议”：事实用陈述句，未实施方案标注“提议/未实施”。
- 不写“应该没问题”“理论上”这类无法验证的结论；写清验证方式与未覆盖范围。
- 中文为主，代码标识符、路径、协议字段保留英文原文。

## 7. 审查与巡检

**每次提交前**（自审）：

- [ ] 断链检查通过；
- [ ] 没有复制出第二份会漂移的配置表；
- [ ] 改动的代码区域在上表的对应文档已同步；
- [ ] 历史文档没有被当作现行说明引用。

**每个版本发布前**（见 VERSIONING）：核对 README、CONFIGURATION、HTTP-API、CHANGELOG 四处。

**每季度一次**文档巡检：随机抽取 5 篇现行文档，按“命令能否跑通、默认值是否一致、链接是否有效”
验证，结果记入 `docs/reviews/`。
